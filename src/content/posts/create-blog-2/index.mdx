# Content란?

[Astro Content Collection 문서](https://docs.astro.build/en/guides/content-collections/)

Astro에서는 일정한 형식을 가진 데이터들을 content로 정의하여 관리할 수 있습니다.

Astro에서는 다음과 같은 상황일때 컨텐츠를 사용하도록 권장하고 있습니다.

- 퍼포먼스가 주요 관심 사안이고 데이터를 빌드 타이밍때 접근하고 싶을 때
- 데이터가 동적이지 않을 때(블로그 포스트, API 문서, 제품 설명서 등)
- 캐싱과 빌드 타이밍에서의 최적화를 사용하고 싶을 때
- 이미지 최적화나 MDX 처리가 필요할때
- 데이터를 한번만 불러와 여러 빌드에 사용하고 싶을 때

여기에서 대부분 말하는 내용들의 키워드는, **빌드 타임에, 높은 최적화 수준과, 정적인 데이터 처리가 필요한 데이터들**을 정의하고 처리하는 것을 목표로 확인할 수 있습니다.

이런 특징 때문에 - Astro에서는 실시간으로 데이터가 업데이트되어야 하거나, DB에서 데이터를 불러와야 하는 등의 동적 데이터에 대해서는 Content를 사용하지 말 것을 권장하고 있습니다.

## Content의 Schema 설정

Astro에서는 [Zod](https://zod.dev/)를 활용하여 Content Collection의 스키마를 정의합니다.

이 스키마는 빌드 타이밍때 파싱되어, 프로젝트의 `.astro` 폴더에 이용 가능한 타입 파일로 저장됩니다.

아래 이미지에서 볼수 있는 것처럼, 이렇게 빌드 타이밍때 생성된 타입은 IDE에게 자동 완성을 위한 Context, 그리고 빌드 타임에서의 타입 체크를 지원하게 됩니다.
![content_autocomplete](./content_autocomplete.png)

## 이 블로그에서의 적용

현재 이 블로그에서는 3개의 요소에 Content Collection을 이용한 데이터 관리를 하고 있습니다.

### 블로그 포스트

당연하겠지만, 블로그 포스트는 위 조건들에 완벽히 부합하는 데이터셋이며, FrontMatter로 title, tags, locale 3개의 필드를 정의하고, mdx를 빌드 타이밍에 처리하여 static HTML로 출력하도록 만들었습니다.

퍼포먼스가 주요 사항이고, 빌드 타이밍때 페이지가 완성되어야 하며(그래야 크롤링 엔진이 완성된 데이터를 들고 갈 수 있으니까요), 데이터가 정적입니다.

포스트 Collection은 아래와 같이 정의되어 있습니다.

```ts
const post = defineCollection({
  loader: glob({ base: "./src/content/posts", pattern: "./**/*.{md,mdx}" }),
  schema: z.object({
    title: z.string(),
    locale: z.enum(["en", "ko"]),
    tags: z.array(reference("tags")),
  }),
});
```

`loader`는 Content를 불러오는 loader에 대해 정의하는 부분으로, 여기서는 `glob` 로더를 사용해 `./src/content/posts` 폴더 아래의 모든 md/mdx 파일을 불러오도록 설정하였습니다.

여기에서의 schema는, md/mdx 파일에서 작성하는 FrontMatter로, 컴파일 시점에 접근 가능한 데이터들입니다.

예를 들어, 이 글에서의 FrontMatter는 다음과 같이 정의되어 있습니다.

```mdx
---
title: 나만의 개발 블로그/포트폴리오 만들기 2 - Content, Path Variable과 Static Paths
tags: [frontend]
locale: ko
---
```

이렇게 정의된 데이터들은, Content의 `data` 프로퍼티에서 접근 가능합니다.

현재 이 글을 컴파일하기 위해 사용하는 Page는 아래와 같은 방식으로 데이터를 불러와 사용합니다.

_코드의 간략한 설명을 위해, heading을 불러와 Navbar에 주입하는 부분, path를 정의하는 부분 등에 대한 코드는 생략했습니다._

```astro
---
const { post } = Astro.props;

const { Content, remarkPluginFrontmatter, headings } = await render(post);
const filtered_headings = headings.filter((heading) => heading.depth < 3);
const { title, tags, locale } = post.data;
const menus = getDefaultNavMenus(locale);
---

<DefaultLayout title={post.data.title} menus={menus} locale={locale} do_index>
  <div>
    <div class="flex flex-col gap-0.5 mb-4">
      <p class="font-bold text-3xl">{post.data.title}</p>
      <p class="text-secondary-foreground text-lg">
        Written on : {remarkPluginFrontmatter.pubDate}
      </p>
      <p class="text-secondary-foreground text-lg">
        {remarkPluginFrontmatter.minutesRead}
      </p>
    </div>
    <div class="flex flex-col gap-1.5 pl-2 pr-5" id="post-content">
      <Content />
    </div>
  </div>
</DefaultLayout>
```

`post.data`에 아까 언급한 것처럼, zod에서 불러온 타입이 이미 정의되어 있기 때문에, 자동 완성이나, 타입 체크를 지원합니다.

### 포스트 태그

블로그 포스트의 내용을 분류하는 태그 또한 Content Collection으로 정의되어 있습니다.

```ts
const tags = defineCollection({
  loader: glob({ base: "./src/content/tags", pattern: "*.json" }),
  schema: z.object({
    name: z.string(),
    description: z.string(),
    related: z.array(reference("tags")),
  }),
});
```

이 태그들은, 차후에 포스트들을 태그를 통해 검색하는 등의 기능을 구현할 때 사용될 예정이며, name, description 등은 UI에 실제로 표현되는 내용으로 사용될 예정입니다.

여기에서 위의 블로그 포스트에서 설명하지 못했던 내용에 대한 설명을 할 수 있는데요, 바로 `reference()` 스키마 정의입니다.

`reference()`는, 다른 Content Collection을 참조하는 스키마 정의 함수로, 생성되는 타입도 `string`이 아닌, 파싱 가능한 Content Entry 타입입니다.

위의 블로그 포스트, 그리고 이 태그 스키마에서도 `z.array(reference("tags"))`를 사용하여 태그 참조를 표현하는 배열 타입으로 정의할 수 있음을 볼 수 있습니다.

아래 사진은 `post` Collection에 정의된 `tags` 프로퍼티의 타입을 보여주는데, `tags` Collection 자체보다는, 이를 불러올 수 있는 레퍼런스 타입임을 확인 가능합니다.

### Localization

다국어 관련 내용도 Content Collection으로 정의되어 있습니다.

다만, 이 컬렉션은 Astro에서 직접 정의하기보다, 현재 블로그에서 사용 중인 다국어 플러그인 `intlayer`가 관리하기 때문에, `content.config.ts`에 정의되어 있지는 않습니다.

```ts
import { t, type Dictionary } from "intlayer";

const postsContent = {
  key: "posts",
  content: {
    title: t({
      en: "Recent Writings",
      ko: "최근 작성된 글",
    }),
    description_1: t({
      en: "Writings about my experiences, thoughts, and interests.",
      ko: "여러분께 이야기하고 싶은 경험, 생각, 관심사를 공유합니다.",
    }),
    description_2: t({
      en: "Roughly two posts per month - but I try to post as often as possible.",
      ko: "한달에 약 2개 정도의 글을 올리지만, 가능한 한 자주 올리기 위해 노력합니다.",
    }),
  },
} satisfies Dictionary;

export default postsContent;
```

# Path Variable 그리고 Static Paths

[Astro의 Dynamic Routes 문서](https://docs.astro.build/en/guides/routing/#dynamic-routes)

### Path Variable

Content Collection이 동적이지 않은 데이터를 빌드 타임에 접근하기 위한 것이라면, 이런 동일한 schema의 컨텐츠들을 실제로 웹 페이지에 보여주기 위해서
페이지를 Path Variable이 포함되도록 정의해주고, 어떤 데이터가 어느 Path에 존재하는지를 Astro에게 알려줘야 합니다.

먼저, Path Variable을 페이지에서 사용하도록 정의하기 위해서는, 파일명에 `[변수명].astro` 등으로 표현하여 페이지의 Path variable을 정의합니다.

만일 여러 세그멘트가 들어올 것으로 예상된다면, 앞에 `...`을 붙입니다.

일례로, 현재 포스트를 보여주는 페이지는 `pages/post/[...postid].astro`로 정의되어 있습니다.

### Static Paths

Path Variable이 존재하더라도, Astro에서는 이 안에 어떤 값이 들어올지 모르기 때문에, 미리 들어올 수 있는 페이지들을 route를 통해 정의해주어야 합니다.

이 route들을 Static Paths라고 하고, 이 Static Paths를 Astro에 제공하기 위해 `getStaticPaths()` 함수를 export합니다.

```ts
export const getStaticPaths = (async () => {
  const posts = await getCollection("post");
  return posts.flatMap((post) => {
    if (post.filePath === undefined) return [];
    const postId = getContentKey(post.filePath);
    return {
      params: { postid: postId },
      props: { post },
    };
  });
}) satisfies GetStaticPaths;
```

위 코드는 블로그 포스트의 `getStaticPaths()` 함수로, 위에서 정의되었던 post 컬렉션을 불러와, 이를 Static Paths로 변환하고, 각 Route에 Post 데이터를 Prop으로 넘겨주는 것을 확인 가능합니다.

post를 랜더링 시점에 다시 불러오기보다 props로 넘기는 이유는, getStaticPaths는 페이지를 파싱해오는 한번만 이뤄지지만, 페이지에 정의된 스크립트는 페이지 하나를 빌드할때마다 호출되기 때문입니다.

이러한 빌드 타임에서의 최적화는 tags collection을 관리할 때도 확인할 수 있습니다.

```ts
import { getCollection } from "astro:content";

let tagsPromise: ReturnType<typeof getCollection<"tags">> | undefined;

export function getTags() {
  return (tagsPromise ??= getCollection("tags"));
}

export async function getTagsMap() {
  const tags = await getTags();
  return new Map(tags.map((tag) => [tag.id, tag]));
}
```

tags collection을 한번 불러오고, 그 후 사용할 때마다 이를 새로 불러오는 것이 아닌, 해당 ts 모듈 scope 안에서 저장되고 관리되기 때문에, tags collection은 한번만 로드되게 됩니다.

### Pagination

[Astro Pagination Guide](https://docs.astro.build/en/guides/routing/#pagination)

Astro에서는, 큰 사이즈의 리스트를 자동으로 잘라 Pagination을 제공하는 API를 지원하고 있습니다.

이 블로그에서는, 이를 이용하여 Post List를 미리 컴파일하고, 이를 유저 스크롤을 인식해 불러오도록 하고 있습니다.

```ts
export const getStaticPaths = (async ({ paginate }) => {
  const posts = await Promise.all(
    (await getCollection("post")).map(async (post) => {
      return {
        post: post,
        renderResult: await render(post),
      };
    }),
  );

  const paths = localeMap(({ locale }) =>
    paginate(
      posts
        .filter((p) => p.post.data.locale === locale)
        .toSorted((a, b) => {
          const aPubDate = a.renderResult.remarkPluginFrontmatter.pubDate;
          const bPubDate = b.renderResult.remarkPluginFrontmatter.pubDate;
          // Compare string dates - older as last
          if (aPubDate > bPubDate) {
            return -1;
          }
          if (aPubDate < bPubDate) {
            return 1;
          }
          return 0;
        }),
      {
        params: { locale: getPrefix(locale).localePrefix },
        pageSize: 10, // Element counts per page
      },
    ),
  );

  return paths.flat();
}) satisfies GetStaticPaths;
```

이 페이지는 `pages/[...locale]/posts/fragment/[page].astro`입니다. Path variable이 2가지고, 둘 다 정적인 데이터기 보다는 라이브러리로 생성되는 데이터기 때문에,
배열과 map을 적극적으로 활용하여 Static Path를 생성하는 것을 학인할 수 있습니다.

포스트를 주어진 locale에 따라 필터링하고, 이를 최신 순으로 정렬하여 `paginate`를 이용해 페이지를 나누는 것을 보여주고 있습니다.
